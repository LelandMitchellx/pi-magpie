# 5. Gateway 与 Web 单进程收敛、8317 默认端口与随机访问密钥设计

## 状态
已采纳 (Accepted)

## 决策背景
在先前版本中，pi-magpie 采用了两阶段多进程策略：在后台先通过 `magpie serve` 拉起独立的网关进程（监听 3425 端口），当用户执行 `/magpie web` 时再额外启动一个 `magpie web` 守护进程（监听 3430 端口），且采用固定的硬编码访问密钥。
该方案存在以下痛点：
1. **多进程资源冗余与生命周期割裂**：后台存在两个独立 ChildProcess，维护复杂，容易发生其中一个异常退出导致状态不一致；
2. **端口冲突风险**：官方默认的 3425 端口常被开发者其他环境或外部全局服务占用；
3. **固定凭证安全隐患**：旧版使用固定的固定字符串作为 Web 访问密钥，若被局域网嗅探或多用户复用存在越权风险；
4. **上游原生能力契约**：根据 Magpie 官方架构（`web.go`），`magpie web` 原生即在同一进程内启动嵌入式 Gateway，完全具备“单进程双监听（Gateway + Web）”的能力。

## 架构决策与选型

经过 Grilling 审讯决策与用户明确授权，我们全面收敛为**单进程统一服务治理架构**：

1. **单进程统一生命周期 (Unified Single Process)**：
   - 后台自愈与 Web 唤起统一收敛为单个后台子进程：`magpie web --addr 127.0.0.1:3430 --no-open`；
   - 该进程在单一进程内同时承载模型网关路由（Gateway）与浏览器控制台（Web Dashboard）；
   - `stopGateway` 与 `stopWeb` 统一收敛为停止当前宿主拉起的这一个统一进程句柄，状态原子重置。

2. **默认网关端口改为 8317**：
   - 统一服务拉起时注入环境变量 `MAGPIE_ADDR=127.0.0.1:8317`（支持用户通过 `process.env.MAGPIE_ADDR` 显式覆盖）；
   - Web 控制台保持监听在 `127.0.0.1:3430`；
   - 所有内部 CLI 命令（如 `healthcheck`、`pi <model>`、`pi effort <level>`）均统一透传 `MAGPIE_ADDR`，确保配置写入正确的网关端口；
   - **向后兼容与迁移**：若需继续沿用旧版 3425 端口或外部网关，设置环境变量 `export MAGPIE_ADDR=127.0.0.1:3425` 即可。

3. **每次启动生成随机安全密钥 (Ephemeral Random Web Key)**：
   - 摒弃旧版静态硬编码 Key，改用 `randomBytes(32).toString("hex")` 动态生成 64 字符的密码学强随机密钥；
   - 密钥仅在当前插件实例内存中持有，每次拉起新统一服务时更换；
   - 在当前服务生命周期内，多次打开浏览器 Web 页面复用该内存密钥链接；服务重启后自动轮换；
   - 外部独立运行的 Web 服务不强行注入该密钥，使用其原有的登录与认证凭据。

4. **严格的外部进程保护与隔离**：
   - 启动前如果检测到网关或 Web 服务已在外部健康运行，则仅复用连接，**绝不标记为本会话拉起**；
   - 执行退出清理或停止命令时，**绝对不误杀外部已有的常驻服务**。

## 方案收益与权衡对比
- **进程开销减半**：仅保留单个后台进程，减少文件句柄与 Node 子进程监控开销；
- **零安全死角**：随机密钥杜绝了凭证泄露风险；
- **状态一致性**：Gateway 与 Web 一损俱损、一荣俱荣，避免“网页打得开但网关挂掉”的半死状态。
