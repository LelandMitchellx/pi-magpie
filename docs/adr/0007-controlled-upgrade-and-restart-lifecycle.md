# 7. 受控升级重启与生命周期重绑定机制

## 状态
已采纳 (Accepted)

## 决策背景与核心痛点
在长期运行和日常开发中，本地 Magpie 存在版本迭代与升级需求。但在旧有架构中，更新操作带来了严重的生命周期脱节缺陷：
1. **进程 PID 裂变脱管**：当用户在 Magpie Web 控制台内部触发版本更新并重启，或通过外部命令热重启时，原父子进程关系中断。旧 Magpie 进程退出触发了插件的 `child.once("exit")` 回调，导致内存中的 `serviceProcess` 句柄被置为 null；
2. **磁盘信标状态失真**：磁盘上的 `~/.pi/agent/magpie-managed.json` 仍静态记录着已退出的旧 PID。在后续调用中，`getManagedService()` 检测到旧 PID 已死，误将该信标文件删除并返回 null；
3. **会话退出销毁短路（孤儿进程驻留）**：当当前 Pi 窗口或所有活跃窗口关闭时，`terminateManagedServiceIfLastClient()` 无法检索到托管元数据，直接放弃终止操作。更新后拉起的新 Magpie 进程彻底沦为孤儿进程常驻在 3430/8317 端口；
4. **新会话误判为外部第三方常驻服务**：后续打开的全新 Pi 终端通过端口探活成功，但因信标文件为空，误将其归类为“外部常驻服务”，永远丧失对其生命周期的回收能力；
5. **Windows 平台文件写入锁 (Text File Busy)**：在 Windows 等操作系统中，运行中的可执行文件会被操作系统句柄锁定，直接覆盖写入或更新会触发拒绝访问 (`EBUSY` / `Access is denied`)。

## 架构决策与选型

经过多方案权衡与用户确认，我们推行**闭环受控更新重启与双引擎升级体系**：

1. **子命令驱动的受控闭环流程 (Controlled Upgrade Sequence)**：
   - 在已有的 `/magpie` 极简 Slash 指令下扩充 `upgrade`、`update` 与 `restart` 子命令（如 `/magpie upgrade`）；
   - **步骤一（释放占用）**：检查当前若由本会话托管运行，先主动执行优雅停止（`stopGateway(true)`），等待 600ms 宽限期释放端口与文件句柄；
   - **步骤二（双引擎安全更新）**：
     - **原生 CLI 优先**：调用官方原生 `magpie update`，复用其 SHA-256 校验与镜像解析逻辑；
     - **内置流式下载兜底**：若原生更新失败或环境异常，自动平滑回退至插件内置流式下载器从 GitHub Releases 原子拉取落盘；
   - **步骤三（受控拉起与重绑定）**：调用 `ensureGateway()` 重新拉起最新版本，自动采集新生成的 PID 写入信标，将子进程句柄重新收敛至 `serviceProcess`；
   - **步骤四（访问密钥无缝继承）**：拉起新进程时优先沿用已有分配的 `webKey`，确保浏览器已打开的控制台无需重新登录或更新 URL。

2. **支持快速自愈重启 (`/magpie restart`)**：
   - 提供显式重启指令，在不执行二进制下载的情况下完成对运行中网关的平稳下线、重新拉起与 PID 重绑定，便于开发者快速排除配置加载异常。

## 方案收益与权衡对比
- **生命周期永不脱缰**：更新与重启后的 Magpie 实例全程处于 Pi 协同信标管控之下，宿主退出时准时清退，彻底杜绝孤儿进程；
- **跨平台安全更新**：先停机后更新，规避 Windows 环境下正在运行二进制的文件写冲突；
- **零上下文污染**：不暴露多余 Tool，维持单个 `/magpie` 命令入口，通过参数解析自然拓展。
